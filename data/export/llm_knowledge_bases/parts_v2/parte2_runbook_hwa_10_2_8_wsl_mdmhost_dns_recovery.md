# PARTE2 RUNBOOK HWA 10 2 8 WSL MDMHOST DNS RECOVERY

## RUNBOOK: Runbook: MDMHOST DNS Loss → "not got the latest Symphony file version" (HWA 10.2.8 WSL2)

**Arquivo de origem:** `data/runbooks/hwa-10.2.8-wsl-mdmhost-dns-recovery.md`

### Resumo executivo

O sintoma "not got the latest Symphony file version" ao subir o agente dinâmico
**não era corrupção de plano** — era **perda do alias `MDMHOST` no `/etc/hosts` do
WSL** (regenerado automaticamente pelo WSL após um boot). Sem o alias, o agente
não consegue registrar recursos no master (`AWSITA366E Could not resolve hostname`),
o broker não linka, o master deslinka as workstations em loop e o Symphony novo
(run N) nunca chega ao agente, que permanece no run N-1.

**Correção:** restaurar `127.0.0.1 MDMHOST` no `/etc/hosts` + `[network]
generateHosts = false` no `/etc/wsl.conf`. **Não é necessário `planman reset` nem
`JnextPlan`** (seriam destrutivos e não resolveriam o problema).

### Causa raiz

- `/etc/hosts` do WSL é **regenerado a cada boot** (comportamento padrão;
  cabeçalho do arquivo diz: "This file was automatically generated by WSL").
- Edições manuais (como o alias de lab `MDMHOST`) **são perdidas** a menos que
  `[network] generateHosts = false` esteja em `/etc/wsl.conf`.
- `JobManager.ini` e `JobManagerGW.ini` referenciam `MDMHOST` em:
  - `EventProcessorHostname`
  - `FullyQualifiedHostname`
  - `ResourceAdvisorUrl` (`https://MDMHOST:31116/JobManagerRESTWeb/JobScheduler/resource`)
  - `BackupResourceAdvisorUrls`
  - `JobManagerGWURIs`
- O serviço REST em si **não caiu**: `curl https://localhost:31116/twsd/` → 200;
  apenas o nome `MDMHOST` não resolvia (`curl https://MDMHOST:31116/twsd/` → 000).

### Cadeia de sintomas (o que observar)

| Componente | Log | Sintoma |
|---|---|---|
| JobManager (agente dinâmico) | `stdlist/JM/JobManager_message.log` | `AWSITA081E` wrapping `AWSITA366E ... Could not resolve hostname` (flood ~60s) |
| Mailman | `stdlist/logs/YYYYMMDD_TWSMERGE.log` | `AWSDEB052E getaddrinfo: Name or service not known` + `AWSBCV035W Mailman was unable to link to workstation: MDM_DWB` |
| Batchman | `stdlist/logs/YYYYMMDD_TWSMERGE.log` | `AWSBDY103I Received command MY:UNLINK for run number 18 ...` em loop |
| conman | `conman showcpus` | Agente no run N-1 sem estado LTI (ex.: `MDMDA 17` vs `MDM 18`) |
| engineServer | `stdlist/appserver/engineServer/logs/messages.log` | `AWSDPM001I ... will be notified about a new available configuration` (deploy OK, entrega falha) |

### Diagnóstico (passo a passo, somente leitura)

```bash
# 1. O arquivo de plano ativo é o que o batchman mantém aberto — NÃO o Sinfonia legado
ps -eo pid,args | grep batchman | grep -v grep
ls -l /proc/<batchman-pid>/fd | grep -iE "sinf|sym"      # esperado: -> /opt/hwa/TWSDATA/Symphony

# 2. Versão do plano: DB × arquivo × run das workstations
su - wauser -c 'source /opt/hwa/TWS/tws_env.sh; planman showinfo'   # Run number, Plan last update
ls -la /opt/hwa/TWSDATA/Symphony /opt/hwa/TWSDATA/Sinfonia          # Symphony deve ser o mais novo
su - wauser -c 'source /opt/hwa/TWS/tws_env.sh; conman showcpus'     # RUN por workstation

# 3. O serviço está de pé? (distingue DNS de engine down)
curl -sk -o /dev/null -w '%{http_code}\n' https://localhost:31116/twsd/    # 200 = engine OK
curl -sk -o /dev/null -w '%{http_code}\n' https://MDMHOST:31116/twsd/      # 000 = nome não resolve

# 4. DNS: o alias existe?
getent hosts MDMHOST        # falha = causa raiz confirmada
cat /etc/hosts              # verifique se a entrada sumiu (regeneração do WSL)
cat /etc/wsl.conf           # generateHosts presente?

# 5. Hostnames usados pelos configs do JobManager (fonte da verdade)
grep -n "MDMHOST" /opt/hwa/TWSDATA/ITA/cpa/config/JobManager.ini /opt/hwa/TWSDATA/ITA/cpa/config/JobManagerGW.ini
```

**Regra de discriminação:** master saudável (batchman LIVES no run N, `planman
showinfo` consistente, `Symphony` atualizado pelo deploy) + agente preso no run
N-1 sem link = problema de **entrega/comunicação** (DNS, rede, certificado) →
não toque no plano. `planman reset`/`JnextPlan` são para corrupção real do plano.

### Correção (não destrutiva, reversível)

```bash
# 0. Backup
cp -a /etc/hosts /etc/hosts.bak-$(date +%Y%m%d-%H%M%S)
[ -f /etc/wsl.conf ] && cp -a /etc/wsl.conf /etc/wsl.conf.bak-$(date +%Y%m%d-%H%M%S)

# 1. Alias imediato (troque MDMHOST pelo hostname que aparecer no passo 5 do diagnóstico)
printf '127.0.0.1\tMDMHOST\n' >> /etc/hosts

# 2. Persistência: impedir o WSL de regenerar /etc/hosts no próximo boot
printf '\n[network]\ngenerateHosts = false\n' >> /etc/wsl.conf

# 3. Verificar
getent hosts MDMHOST
curl -sk -o /dev/null -w '%{http_code}\n' https://MDMHOST:31116/twsd/    # agora 200
```

> Alternativa de persistência: adicionar `127.0.0.1 MDMHOST` ao hosts do Windows
> (`C:\Windows\System32\drivers\etc\hosts`) — o WSL incorpora essas entradas
> durante a regeneração automática.

### Recuperação automática (sem intervenção manual)

Não é preciso `conman link` nem `conman start` — os ciclos do TWS fazem tudo:

| Hora | Evento observado |
|---|---|
| +27s | `AWSITA083I Resource information was sent` (agente registra recursos; ~1min de ciclo) |
| +8min | `conman showcpus`: todas as workstations **LINKED no run 18** (`MDMDA ... LBI J M`, `MDM_DWB ... LTI JW`, `MASTERAGENTS ... LBI J`) |
| +10min | Jobs reais completando `SUCCESSFULLY` no MDMDA (`MDMDA#...DS_CHAIN_A ... has completed SUCCESSFULLY`) |

O Symphony run N (já deployado) chega ao agente automaticamente assim que a
comunicação volta.

### Prevenção

1. `generateHosts = false` no `/etc/wsl.conf` (feito acima) — ou alias no hosts do Windows.
2. Após qualquer `wsl --shutdown` / reboot, checar:
   ```bash
   getent hosts MDMHOST || echo "ALIAS PERDIDO - ver runbook"
   ```
3. Monitorar `JobManager_message.log` por `AWSITA081E/AWSITA366E` (flood = DNS).
4. Não confundir `Sinfonia` (legado, timestamp estático) com `Symphony` (ativo).
